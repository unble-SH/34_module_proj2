## 1. 입력

모듈 2 출력. 팀원 JSON에서 `violated_laws`가 빠진 형태로 가정한다.

```json
{
  "scan_id": "SCAN-2026-001",
  "scan_date": "2026-10-02",
  "target_system": "모의 교육 플랫폼",
  "findings": [
    {
      "item_id": "U-01",
      "title": "root 계정 원격접속 제한",
      "status": "취약",
      "severity": "상",
      "asset": { "name": "회원 DB 서버", "handles_personal_data": true },
      "evidence": "sshd_config PermitRootLogin yes"
    }
  ]
}
```

`evidence`(판정 근거)는 있으면 LLM 판단에 쓰고, 없으면 title만으로 판단한다.

## 2. 데이터 소스 (로컬 txt, API 사용 안 함)

| 파일 | 용도 | 상태 |
|---|---|---|
| 개인정보 보호법(법률)(제21445호)(20260911).txt | 조문 후보 목록, 조문 원문(text) | 있음 |
| ISMS-P 인증기준 안내서(2023.11).txt | 101개 기준 목록, 기준별 관련 법규(검증용 정답표), 결함사례 | 있음 |
| 개인정보의 안전성 확보조치 기준(고시) txt | 제5조 접근권한의 관리, 제6조 접근통제 등 기술 조문 | 법제처에서 받아 변환 필요 |

### 2.1 법령 txt 파싱 규칙 (팀원 요청 반영)

1. **부칙 제외**: `부칙 <제21445호,` 줄 이후는 후보 목록과 추출 대상에서 뺀다. 부칙 제1조~제4조가 본문 제1조~제4조와 번호가 겹치기 때문.
2. **현행본 선택**: 같은 조문이 두 벌이면 `[시행일: ...]` 표시가 없는 쪽이 현행본. text에는 현행본을 넣고 `in_force: true`. 예정본(제2조, 제7조의9, 제28조의14, 제32조의2, 제75조의 2027년 시행 버전)은 쓰지 않는다.
3. **후보 목록**: 중복 제거한 현행 조문만으로 만든다. 항목은 `조번호 + 제목` (예: `제29조(안전조치의무)`).
4. 조문 경계: `^제\d+조(의\d+)?\(` 로 시작하는 줄이 조문 시작. 다음 조문 시작 전까지가 본문. 장·절 제목 줄(`^제\d+장`, `^제\d+절`)은 건너뛴다.

### 2.2 ISMS-P txt 파싱 규칙

- 기준 시작: `^[123]\.\d{1,2}\.\d{1,2} ` 줄 (예: `2.6.6 원격접근 통제`).
- 구역: `[인증기준]`, `[주요 확인사항]`, `[관련 법규]`, `[세부 설명]`, `[증거자료 예시]`, `[결함사례]`.
- LLM 후보 목록에는 번호와 이름(필요하면 [인증기준] 한 문단)만 넣는다. 101개 전부 넣어도 길지 않다.
- `[관련 법규]`가 법 조문 매핑의 유일한 출처다 (규칙 기반).

## 3. 처리 흐름

```
입력 findings
  └─ status == "양호" → violated_laws: [], isms_p: [] 그대로 통과
  └─ status == "취약" / "수동확인"
       1) 프롬프트 구성: 취약점 설명(title, evidence, asset) + ISMS-P 101개 기준 목록 + 법령 조문 후보 목록
       2) OpenAI 호출 (구조화 출력 JSON): 해당 isms_p 기준 번호 목록 + 기준별 reason
       3) 검증: ISMS-P 번호가 101개 목록에 있는지 확인 → 없으면 버림
       4) 조문 매핑(규칙): 고른 기준의 [관련 법규]를 파싱해 조문 목록 생성, mapped_by "rule"
       5) 조문 원문을 txt에서 꺼내 text에 채움, law_code/ref_id/effective_date/in_force 채움
          txt에 없는 조문이면 reviewed false + 사유
  └─ 팀원 형식 JSON으로 출력
```

- **ISMS-P 기준 선택은 LLM**, **법 조문은 규칙 기반**: LLM이 고른 기준의 `[관련 법규]`에 적힌 조문을 코드가 가져온다 (`mapped_by: "rule"`). LLM은 조문을 고르지 않는다.
- `[관련 법규]`가 없는 28개 기준(주로 1.x 관리체계, 2.8~2.12 운영 항목)에 걸리면 `violated_laws`는 빈 배열로 둔다. LLM으로 채우지 않는다 (법 위반 과장 방지, 팀 합의 2026-10-02).
- 조문 원문(text)은 txt에서 복사한다. 가져온 조문 번호가 txt에 있는지, 제목이 일치하는지 코드로 확인하고 다르면 `reviewed: false`에 사유를 남긴다 (안내서 2023.11 vs 법 2026.9 시행본 차이 대비).
- 원문을 가진 법령: 개인정보 보호법, 안전성 확보조치 기준, 정보통신망법(추가 예정). 그 외 법령(소방시설법 등)은 text null, 조문 번호와 ref만 남긴다.
- `asset.handles_personal_data`가 false면 개인정보 보호법 조문은 후보에서 빼거나 reason에 "개인정보 미처리 자산" 표시. (시나리오상 지금은 전부 true)

## 4. LLM 프롬프트 요점

- 역할: 정보보호 컨설턴트. 주어진 목록 밖의 조문·기준을 절대 만들지 말 것.
- 입력으로 주는 것: 취약점(item_id, title, evidence, asset), ISMS-P 기준 목록(번호 + 이름), 법령 조문 후보 목록(법령명 + 조번호 + 제목).
- 출력 형식(JSON만):

```json
{
  "isms_p": [ { "criterion_id": "2.6.6", "title": "원격접근 통제", "reason": "..." } ],
  "violated_laws": [ { "law_name": "개인정보 보호법", "article_no": "제29조", "reason": "..." } ]
}
```

- temperature 0, OpenAI API 사용 (팀 보유 키). 모델은 gpt-4o-mini(속도·비용) 또는 gpt-4o. 키는 .env의 OPENAI_API_KEY.
- API 실패 시: 캐시된 이전 결과를 쓰고 `source`에 "cache" 표시. 캐시도 없으면 violated_laws 빈 배열 + 오류 로그.

## 5. 출력 (모듈 4로 넘기는 형식)

팀원이 제시한 형식 + 추가 필드 3개(`reason`, `in_force`, `isms_p`).

```json
{
  "scan_id": "SCAN-2026-001",
  "scan_date": "2026-10-02",
  "target_system": "모의 교육 플랫폼",
  "findings": [
    {
      "item_id": "U-01",
      "title": "root 계정 원격접속 제한",
      "status": "취약",
      "severity": "상",
      "asset": { "name": "회원 DB 서버", "handles_personal_data": true },
      "isms_p": [
        { "criterion_id": "2.6.6", "title": "원격접근 통제", "reason": "관리자 계정의 원격 직접 접속을 제한하지 않음" },
        { "criterion_id": "2.5.5", "title": "특수 계정 및 권한관리", "reason": "root 특수 권한 계정이 통제 없이 사용 가능" }
      ],
      "violated_laws": [
        {
          "law_code": "PIPA-29",
          "law_name": "개인정보 보호법",
          "article": "제29조(안전조치의무)",
          "text": "개인정보처리자는 개인정보가 유출등이 되지 아니하도록 ... 조치를 하여야 한다.",
          "reason": "root 원격 직접 접속 허용은 접근통제 미비로 안전성 확보에 필요한 기술적 조치 미이행에 해당",
          "source": "국가법령정보센터 원문(법률 제21445호)",
          "effective_date": "2026-09-11",
          "in_force": true
        },
        {
          "law_code": "SAFE-6",
          "law_name": "개인정보의 안전성 확보조치 기준",
          "article": "제6조(접근통제)",
          "text": "...",
          "reason": "...",
          "source": "국가법령정보센터 원문(개인정보보호위원회 고시)",
          "effective_date": "...",
          "in_force": true
        }
      ]
    },
    {
      "item_id": "U-02",
      "title": "패스워드 복잡성 설정",
      "status": "양호",
      "severity": "상",
      "asset": { "name": "회원 DB 서버", "handles_personal_data": true },
      "isms_p": [],
      "violated_laws": []
    }
  ]
}
```

### 필드 규칙

| 필드 | 규칙 |
|---|---|
| law_code | `법령약어-조번호`. PIPA = 개인정보 보호법, SAFE = 안전성 확보조치 기준. 항·호는 `PIPA-75-2-5`처럼 뒤에 붙임 |
| article | `제29조(안전조치의무)` 조 번호 + 제목 |
| text | txt에서 복사한 현행 조문 원문. LLM 생성 금지 |
| reason | LLM 작성, 한두 문장 |
| source | "국가법령정보센터 원문(법률 제21445호)" 등 출처 + 법령 번호 |
| effective_date | 법령별 시행일. 개인정보 보호법 2026-09-11, 고시는 해당 고시 시행일 |
| in_force | 현행본이면 true |
| 양호 항목 | isms_p, violated_laws 빈 배열 |

## 6. 코드 구성 (Python)

```
module3/
  law_loader.py      # 법령 txt → {조번호: {title, text, in_force}} (부칙 제외, 현행본 선택)
  ismsp_loader.py    # ISMS-P txt → {기준번호: {title, 인증기준, 관련법규[], 결함사례[]}}
  mapper.py          # 프롬프트 구성, Claude 호출, 응답 검증
  builder.py         # 출력 JSON 조립 (law_code, text, source, effective_date, in_force)
  main.py            # 입력 JSON 읽기 → 처리 → 출력 JSON 쓰기
  cache/             # 항목별 LLM 응답 캐시 (시연 대비)
```

## 7. 검증 방법

- U-01 취약 입력으로 돌려서 PIPA-29, SAFE-5, SAFE-6과 ISMS-P 2.6.6, 2.5.5가 나오는지 확인.
- 고른 조문이 ISMS-P 안내서 [관련 법규]와 일치하는 비율 기록 (기획안 검증 방법 4번).
- 양호 입력은 빈 배열로 나오는지 확인.
- 조문 번호를 일부러 틀린 응답을 넣어 검증 단계가 걸러내는지 테스트.
